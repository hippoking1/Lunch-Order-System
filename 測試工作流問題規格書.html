SECTION 01 問題定義
現況 每次改版都要針對目前系統新增及已有的功能進行測試以確認所有功能正常，但目前缺乏系統化測試方法。
痛點
1 手動測試耗時長，且容易因為功能越來越多而遺漏部分邊界情境。
2 因為過度依賴開發者的記憶來測試，導致系統上線容易發生迴歸錯誤 (Regression)。
3 點餐流程涉及前端介面狀態、Google Apps Script 後端邏輯與 Google Sheets 資料庫，排錯與驗證繁瑣。
flag
SECTION 02 目標
P1 ✅ 建立一套核心流程的自動化或標準化測試表，確保改版不會破壞 P0 核心功能（點餐、加點、結帳金額計算）。
P1 ✅ 在一個小時內能完成每次改版的全功能迴歸驗證。
P2 ✅ 能夠無縫整合至現行的開發與部署流程中。
block
SECTION 03 限制條件
CN-01 🚫 系統基於 React + Vite 並打包注入於 GAS HtmlService 執行，一般自動化框架可能難以直接模擬 GAS 執行環境。
CN-02 🚫 缺乏專職 QA 團隊，測試流程的維護成本必須極低，不能反過來拖垮開發進度。
CN-03 🚫 資料庫為 Google Sheets，測試時需解決髒資料清理或環境隔離的問題。
construction
SECTION 04 障礙
OB-01 → 測試環境與正式環境混用
根因：當前架構並未配置專屬的測試版 Google Sheets 作為 Staging 環境，導致無法隨意注入假資料做自動化測試。
影響：測試動作可能污染正式訂單資料，或因害怕弄亂資料而不敢進行極端測試。
OB-02 → GAS 環境難以 E2E 測試
根因：GAS html 頁面有 Google 的 iframe 限制與登入牆，Playwright/Cypress 難以自動化跨越帳號驗證。
影響：只能依賴人工點擊或前端 Mock 測試，無法進行真實的 End-to-End 自動化。
verified
SECTION 05 成功標準
1 完成一份涵蓋 100% P0（點餐/結單/查看狀態）情境的手動檢核清單（Checklist）。
2 至少建立 3 個前端核心商業邏輯（例如：費用計算、加點邏輯）的單元測試並放入 CI/CD 流程。
3 建立分離的 Staging 部署機制與測試專用 Spreadsheet。

SECTION 07 實施計劃
1
Phase 1: 環境隔離與文件化
複製現有 Spreadsheet 建立測試用資料庫，並列出 P0 核心手動測試檢核表（CheckList）。
2
Phase 2: 隔離出 Mock API 環境
在 React 專案中實作 Mock Service Worker 或假資料層，讓前端能在不連 GAS 的情況下運行 90% 畫面。
3
Phase 3: 導入重點單元測試
針對容易出錯的加點邏輯、金額計算加入 Vitest 單元測試，確保邊界條件不被破壞。
4
Phase 4: 自動化部署整合
將單元測試加入部署腳本，每次執行 npm run deploy 時會先跑測試，失敗則阻斷更新。
do_not_disturb
SECTION 08 排除範圍
⛔ 不追求 100% E2E UI 自動化測試（投入產出比太低）。
⛔ 不修改現有 GAS 作為後端與資料庫的基礎架構設定。
⛔ 不引入重型 QA 測試平台管理工具（如 TestRail），以 Markdown 檢核表輕量管理即可。
warning
SECTION 09 風險與假設
⚠️ 假設
⚠️ 手動測試檢核表如果夠明確，可以在 15 分鐘內執行完畢，不會過度消耗時間。
⚠️ 大部分的系統 Bug 是因為前端邏輯錯誤或元件狀態綁定錯誤，而非 GAS 後端系統性崩潰。
⚠️ 風險
⚠️ GAS 的黑箱限制：有時 Google Apps Script 掛掉是 Google 本身配額或 API 異常，自動化測試與 mock 抓不到這種錯誤。
⚠️ 隨著專案變大，手動 CheckList 會越來越長，最終仍然會回到「因為不想花時間測而跳過」的惡性循環。需要嚴格約束或定期轉化為單元測試。
