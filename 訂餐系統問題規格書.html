SECTION 01 問題定義
現況 目前訂餐系統使用純原生 HTML/JS 開發，單一檔案超過 500 行。依賴多次非同步 google.script.run 呼叫來取得連動選單資料（如餐廳、菜單、加點）。
痛點
1 操作延遲：每次切換選項皆需等待 1-2 秒的 GAS 伺服器回應，出現加載動畫，打斷點餐體驗。
2 程式碼維護困難：前後端邏輯與 DOM 操作高度耦合（Spaghetti Code），新增功能容易牽一髮動全身。
3 併發競爭：高頻率讀寫 Google Sheets 導致 LockService 容易遇到超時或資料覆寫風險。
flag
SECTION 02 目標
P1 ✅ 載入菜單與選擇餐廳時的網路請求次數降至 0 次（改為初始一次性載入）。
P1 ✅ 分離前端 UI 與資料狀態管理，減少 50% 的直接 DOM 拼接邏輯。
P2 ✅ 引入輕量化前端套件或模組化工具，提升後續開發效率。
block
SECTION 03 限制條件
CN-01 🚫 平台限制：必須繼續依附於 Google Apps Script 與 Google Sheets 架構下運行。
CN-02 🚫 GAS 記憶體與傳輸限制：單次回傳的 JSON Payload 大小不能無限增加，需控制在合理範圍。
CN-03 🚫 資料庫效能：Google Sheets 單次寫入/讀取速度上限無法突破，無法與正規 SQL 資料庫相比。
construction
SECTION 04 障礙
OB-01 → N+1 查詢導致的卡頓
根因：連動選單（種類->餐廳->菜單）設計為每次選擇才發送請求向 GAS 索取資料。
影響：UI 頻繁出現 loading，造成點餐流程至少有 3-5 秒被浪費在等待回應。
OB-02 → 全域變數與命令式 DOM 更新
根因：未使用狀態管理，完全依賴 insertAdjacentHTML 與手動改變 element 狀態。
影響：Index.html 變得肥大且難以除錯，未來若要新增「多選套餐」等新功能，開發難度極高。
verified
SECTION 05 成功標準
1 使用者開啟頁面後，選擇到完成點餐過程中的 loading 出現次數必須為 0 次。
2 前端 JavaScript 主邏輯依賴的全域變數數量減少至 2 個以內（例如單一 State Object）。
3 單一使用者的完成點餐操作總花費時間（從開網頁到送出完成）降低 30%（約省下 5 秒的網路等待）。

SECTION 06 建議方案
方案 解決 難度 費用
單一 Payload 預載送 (Pre-fetch All) 在 getInitialData 中一次性打包所有餐廳、菜單、加點資料傳回前端，前端以記憶體過濾取代 API 呼叫。 低 低（僅改寫查詢與前端過濾邏輯）
導入輕量化前端框架 (如 Vue / Alpine.js) 引入 Alpine.js 進行宣告式狀態綁定，消除手動 DOM 操作，提升模組化。 中 中（需重構現有 HTML 標籤與綁定）
GAS 現代化建置鏈 (Vite + React) 本機使用 React 開發，透過 Vite 與 plugin 打包出單一 HTML 部署至 GAS，徹底解決維護與狀態問題。 高 高（需全面重寫並建立 CI/CD 或打包腳本）

SECTION 07 實施計劃
1
修改 GAS 後端 getInitialData
彙整餐廳與菜單資料庫表，並將結果編譯為一個巢狀 JSON Object (包含 Category -> Restaurant -> Items)。
2
修改前端連動邏輯
移除 restaurant-select 與 menu-select 的 google.script.run，改為直接過濾預載的 JSON Object。
3
引入狀態管理容器 (輕量)
將散落的全域變數 (currentMenuItems, employeePaymentData 等) 整合併入一個全域 AppState 物件。
4
壓力測試與部署
測試一次載入 500 筆菜單資料的 Payload 是否會超過 GAS 回傳時間限制，確認無誤後上線。

SECTION 08 排除範圍
⛔ 不更換資料庫：不考慮將資料庫從 Google Sheets 遷移至 Firebase 或 SQL。
⛔ 不重寫現有樣式：保留現有的 CSS（Lifestyle Premium），僅針對 JavaScript 效能優化。
⛔ 不開發管理員後台 UI：僅專注於前端點餐流程的體驗改善。
warning
SECTION 09 風險與假設
⚠️ 假設
⚠️ 假設目前的菜單總數量（所有餐廳加總）在未來一年內不會超過 5000 筆（避免單一 JSON Payload 過大導致載入崩潰）。
⚠️ 假設團隊具備基礎的 JSON 操作能力，可以適應從 Database 讀取轉為 Memory 讀取。
⚠️ 風險
⚠️ 若是單一 Payload 過大（>5MB），可能導致首屏載入時間超過 10 秒，反而在剛開網頁時造成更糟的體驗。
⚠️ 多人在同一時間大量送出訂單，Google Sheets 的 LockService 仍有 10 秒等待超時上限，可能導致部份訂單遺失。
